### Symptom → number (reverse lookup)

**People enter by symptom, not by number**. When something goes wrong, start from this column:

| What you see | Check first |
|---|---|
| Mojibake in the source, the line count dropped, syntax errors | **#1** |
| "The code was changed but the behaviour is wrong" | **#2** |
| All gates green, but the page is broken | **#5 #6 #9** |
| An assertion went red, but reading the code shows nothing wrong | **#8 #10** |
| Data is inexplicably missing, or a date is off by one day / the time zone is wrong | **#3 #4 #15** |
| Some can see it and some cannot; a read-only account can still change it | **#7** |
| The script "runs", but what it fetched is wrong | **#11** |
| The feature was built, but the user cannot use it | **#12** |
| The numbers in the document do not match the measurement | **#13** |
| One place was changed and the same kind of problem appeared somewhere else | **#14 #9** |
| A table suddenly has 0 rows, or someone else's things are gone | **#15 #16** |

> How to use it: once you have the number, **read that row's "root cause" and "lesson"** — the same symptom does not mean the same mechanism,
> so do not take #2 (a stale process) for #11 (the tool fetched the wrong thing); the two are fixed in completely different ways.

## 2. Six "general shapes" extracted from the incidents

1. **"Each part is right, and together they are wrong"**: every assertion passes, but nobody tests the path the user will walk.
   ⇒ A critical path needs one **end-to-end** criterion.
2. **"Built ≠ usable"**: the feature is written and the interface works, but there is **no entry point / no permission / no registration**
   ⇒ At delivery you must answer "how does the user get to it".
3. **"The fix itself is a new source of defects"**: one fix touched one line and took the other flags on that line with it.
   ⇒ Assert the hit count before replacing; after the change look at the **knock-on effects** (which apparently unrelated checks went red).
4. **"The single source of truth was destroyed by a routine action"**: a script claiming to be idempotent deleted someone else's section.
   ⇒ A script must guard itself; do not rest correctness on "everyone will be careful".
5. **"The verification environment does not self-prove its version"**: the code was changed, and what got verified was the old process.
   ⇒ Make the environment report its own fingerprint.
6. **"A comment says the opposite"**: one wrong comment had a whole class of defects judged "not a hole".
   ⇒ A judgement must cite a **concrete line number**; neither comments nor verbal conclusions count as evidence; if you find a comment you wrote that contradicts the code, **fix the comment at once**.

## 3. Breakpoints: indexable, recoverable

**The rule**:
1. **Avoid creating unnecessary breakpoints** — finish one thing **in one pass** (change code + sync criteria + green gates + record it); do not leave half of it;
2. **Avoid omissions** — list **all the knock-on points** of one change (criteria, copy, column widths, allowlists, documents) **in full** before starting;
3. **When you must interrupt**: write the breakpoint into the ledger and make sure it **can be found by index** and **is easy to restore** (write down the landing point and the recovery steps).

**In the original words**: **a rollback may happen; a breakpoint must not go missing.**

**Why**: within a single day 某工程 saw several "rolled back half-way through" episodes (criteria not synced, the wrong slice cut, an anchor containing a space).
A rollback is right in itself (**a red light is never banked**), but if the breakpoint is not written into the ledger, the next round has to **survey it all over again** and the time is burnt twice.

**The minimum fields of a breakpoint ledger**: id · status · landing point (file:line / function / commit) · recovery steps · basis.
**Discipline**: anything "meant to be left for the next round" must appear as a line in the ledger **in the same round**.

**Citation**: `docs/00 §A.7`; `docs/25_断点台账.md`.

## 4. Reversible: small steps + marks + a per-increment account

- **At every reversible whole point, make a mark + export an archive package** (including a database dump) and write the account into the repository ⇒
  "which version can be returned to what state" is always findable.
- **A mark, once made, never moves**: rollback = check out the mark, and **do not move the mark**.
- **Red means roll back; a red light must never be banked as one increment**.
- **When a conclusion conflicts with an increment already landed, roll back mark by mark rather than defending it**.

**Why it is worth institutionalising**: with it, "I changed the wrong thing" is just a reversible operation;
without it, a wrong change turns into an argument about "should we take another gamble". 某工程's original words were "roll back tag by tag, and the cost is tiny".

**Citation**: `证据\存档记录.md`; `docs/21_单一实现审计与修正计划.md`.

## 5. Recovery drills: a backup is not a backup until it can be restored

某工程 left a batch of **recovery drill records** here (several drills on the same environment, including one record marked "void · fake pass").
Two lessons:

1. **A drill must judge the "result", not "no error was raised"**: how far the restore went must be **compared item by item** (table count, row count, key values),
   rather than looking at whether the script threw an exception.
2. **If a drill turns out to be a fake pass, mark that record void** and leave it in place rather than quietly deleting it —
   otherwise the next round will take it as "verified".

## 6. How to pick up after the project was interrupted

**The minimum usable recovery entry point** (某工程 wrote it as a "the only entry point after a restart" document, containing):

1. **This round's snapshot**: the latest commit, marks, gate numbers, archive package locations.
2. **Recovery steps**: numbered in order, each step with an executable command (including a "self-proof" step: run a script to prove the environment really came up).
3. **A ready re-check scene**: where the data is, what the sample project is called, which account to log in with.
4. **Boundaries**: what is known, and what this version still cannot verify.

**Two hard requirements**:

- **Every step** in the recovery steps **must be verifiable** (what output you get after running it);
- **When the session changes, the context changes** (temporary areas and isolated instances disappear) ⇒ environment information must state clearly "why it will be gone and how to rebuild it".

**Citation**: `docs/23_交接_重启后继续推进.md`; `docs/09_本地运行服务器.md`; `证据\S4.5_断点与恢复.md`.
