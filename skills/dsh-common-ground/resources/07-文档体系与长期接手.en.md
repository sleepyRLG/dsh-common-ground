> **Distribution copy (desensitised)**: this copy is produced by the generator on the source-project side under a fixed rule.
> It removes the **source information that resolves only on the authors' machine** (project name, drive letters and library paths become stand-ins: `某工程` = the original project).
> Apart from the stand-ins and the annotations (copy notice, language switcher) it matches the source file, and **authority stays on the source-project side**;
> the copy is **recomputable** by the generator (see checks 2 and 3 in the skill's `README.md`).

# 07 · Documentation system and long-term takeover

English | [中文](07-文档体系与长期接手.md)

> This chapter solves one concrete problem: **work on a project with an AI over the long term, the documents pile up, and then the "goal" is lost.**
>
> 某工程 has a self-diagnosis well worth remembering — a goal had long since been scheduled in the plan, **dropped out of view after round-by-round handovers**,
> and was only noticed later. On that basis they set the "index" up as **the first line of defence against loss**. This final chapter of the series is about exactly that.

---

## 1. Admit one thing first: goals do get lost

A judgement that kept recurring in 某工程 (**this is reported speech** — a consensus across many rounds of practice, **no wording that could be checked back verbatim was found in the original**):

> **The goal was not unscheduled; it was lost during round-by-round execution.**

**Why it gets lost**: every round is a new session with a new context. What the previous round "remembered" is not passed on automatically;
and a loose-leaf style handover document (rewritten every round) squeezes the goals that were "already scheduled but not yet done" out of view.
**The countermeasure is not "remembering harder" but "writing it in a place that does not move for a long time, and making every new session pass through it".**

---

## 2. Day 0: the minimum path from zero (the order cannot be reversed)

**Why it is needed**: 某工程 was "start working first, backfill the documents later", and the price was the sentence at the head of this chapter — **goals lost during round-by-round execution**.
The path below is the minimum build order **reverse-engineered** from its incidents. **Every step must have a deliverable; it is not "raising awareness".**

| Step | What to build | Deliverable (missing ⇒ it was not built) |
|---|---|---|
| 1 | **Ruling landing point** | one document holding only: the bullet points of the user's own words / three states / the list of not-yet-ruled items |
| 2 | **Project purpose + foundation-level functions** | one paragraph + one "three things most worth doing now" (ordered by importance to the purpose) |
| 3 | **Glossary** | the single spelling of each key noun + the agreement "on a conflict, tell the user first" |
| 4 | **"What counts as passed"** | **one criterion that can fail** + the three-state reporting format (even if there is only one) |
| 5 | **Priority chain** | who prevails on a conflict, written down |
| 6 | **Boundaries** | which directories／libraries are read-only; which data must not be touched |
| 7 | **Ledger** | todo / pending ruling / breakpoint, **one place each** (do not scatter them) |
| 8 | **The first cut** | walk the whole flow: proposal → ruling → act → gate → three-state report |

**What not to do on day 0**:

- **Do not build the complete three-layer documentation system first** — land it once there are real entries (the clauses in 03／04 of this series all grew out of incidents afterwards).
- **Do not write a "comprehensive design" first**: protection against loss rests on **an index + a single convergence point**, not on writing everything at once.
- **Do not create tables and databases first**: settle "what counts as passed" first, otherwise you cannot judge whether the first cut actually succeeded.

> **Source (three states)**: steps 1, 2, 4, 5 and 7 come from 某工程's practice and incidents; steps 3, 6 and 8 are **this series' arrangement**
> (collecting agreements scattered in various places into one order), **not verified in the field as a whole**.

**Citation**: `docs/00 §11.35`, `§11.36`, `§A.7`, `§A.9`; `docs/13_现状一页纸.md §九`;
`docs/23_交接_重启后继续推进.md`.

---

## 3. Documentation divides into four layers; do not merge them

| Layer | What it governs | Characteristics |
|---|---|---|
| **Ruling layer** | the user's instruction text + execution status (proposed / ruled / not yet ruled) | **highest authority**; append-only, overturned items are kept (struck out + a pointer to the new ruling) |
| **Design layer** | the data-safety iron rules, the source of truth, permissions, structural change, verification discipline, boundaries | **the semantics must hold steady** — once the ruler drifts with every incident, nobody can predict anything |
| **Operational layer** | which tools, in what order, what counts as passed, how to recover from a deviation | **follows the incidents** — immediate patching after stepping in a pit; the more it follows, the more accurate it gets |
| **UI layer** | display · interaction · language | can be derived neither from the data model nor in reverse from the code |

**Why not merge them** (the logic of 某工程's own words): **the design semantics must hold steady while operational discipline follows the incidents**; merged, the two inevitably drag each other down.
So it is **division of labour + pointers**, and on a conflict the priority chain rules:
**a ruling given by the user on the spot > ruling document > design layer > operational layer > index > explanatory document > historical archive**.

**The index itself also needs a maintenance agreement**: a new file is **registered at the same time** (otherwise it is as if it did not exist); a deleted file has its **index line struck at the same time**;
the index **does not restate the semantics** (it says only "what it governs, when to read it"), and where an inconsistency is found, the index is fixed.

---

## 4. Six rules that keep documentation from "drifting"

### 4.1 Pointers, not transcription

**Quotations always use "path + section number", never wholesale transcription.**
One transcription = one extra copy = **certain drift** (when both places "are true", you cannot even tell which one is newer).
The only exception is a transcription explicitly ruled as such, like "carry the operational discipline over in full", and the file head must state that this is a transcription.

### 4.2 Generated artifacts are not hand-written

**Whatever is a "fact" is generated; whatever is "our decision" is hand-written.**
Column names/order/types/comments are generated from the data source; parent-row relations, cancellation semantics, the allowlist and the criteria are hand-written.
Two criteria pin it down: **a generated artifact must match its source**; **a generated artifact must go through the regular gate** (change the source and forget to regenerate ⇒ must go red).

### 4.3 Do not hard-code numbers

**Leaving a number that is bound to become false is worse than not writing one.** Quantities like row counts, item counts and pass counts start expiring the moment they are written into a document.
If you want a number, **measure it now** (give the command that fetches it), or use only relative semantics ("only decreases, never grows").

### 4.4 History is not rewritten

Evidence, execution records and old-version documents are **historical archive and are not changed retroactively**;
an erroneous historical record is **marked as void and left where it is** (otherwise the next round will take it for "verified").

**Citation**: `docs/01 §七` (audit trail, archiving and reversibility); `旧案\实现\证据\作废\README.md`
(the physical artifact of one rehearsal record marked "void · fake pass", in the same directory as `恢复演练_20260915_140850_作废_假通过.md`).

### 4.5 Every rule must have a citation

**A rule with no citation is taken for empty talk.**
So every principle must be traceable back to: an incident, a measurement, or one ruling from the user.
A new principle must **at the same time** be added to the provenance table — otherwise "a rule with no citation" soon turns into a slogan nobody believes.

### 4.6 A reusable artifact carries no project records

**Things like skills, templates, scaffolding and components that "are to be copied into another project and used there" carry only the method and the shape,
not the records, paths, conclusions or disputes of any one project** — those are **project-side** files.

- **Criterion**: copy this thing **verbatim into another project** — does it still hold, and is it still clean?
  If it brings out the previous project's run records, absolute paths or some disputed conclusion ⇒ **it fails**.
- **Write them separately**: the **method** (how to record, which fields to record) stays in the reusable artifact; **the record itself** stays in the project,
  one per project, **never mixed into each other**.
- **Why**: mixing them in spoils two things — **cross-contamination** (others cannot tell which conclusion holds for which project) +
  **non-reusability** (switching projects means deleting the records first, and a missed deletion carries the previous project's site over).
- **What is not a "record"**: **citations and evidence references** (pointers to files of the original project) are **knowledge**, not run records —
  they are fine staying in the body text, but you must **state which project they belong to**, and they are **not distributed with the reusable artifact** (otherwise whoever switches projects holds a path that will not open).
- **"External information" in a distributable artifact**: project name, drive letters, machine-local library paths, references to files that exist only on this machine —
  **either remove them or turn them into stand-ins** (desensitisation). This and "run records" are **two different things**, do not mix them:
  **desensitisation** treats "names that will not open", **moving out** treats "project facts that should not have been mixed in"; the former may stay in the artifact, the latter must go.
- **When switching projects**: the record file name is decided by **that project**, as long as it sits on the project side and is kept apart from the reusable artifact —
  do not write one project's file name (such as `××核对记录.md`) into the general rules.
- Example: this series' skill package (`本技能\`) holds `SKILL.md` + `README.md` + the **desensitised copies** —
  the **method and format** of checking are in the README; the copies **carry only the method content, not the indexable project name or machine-local paths**;
  **the run records land on the project side** (`核对记录.md`), and **do not go into the skill package**.

> **Source (three states)**: this clause comes from a user direction in the 2026 round of this collaboration
> ("the review record is aimed at the project and should not exist in a skill file, lest information from different projects be mixed"), **not from 某工程's original text**.

## 5. Deliver a document that "can be taken over"

**The four things an AI changing sessions needs** (and a new colleague needs too):

1. **What this project is and where it stands now** (one paragraph + one status table, **stable quantities only**).
2. **Which document to read to do a given thing** (an index table searched by situation).
3. **Who prevails when two statements conflict** (the priority chain + a register of "what is already stale").
4. **The single entry point**: where to start, how many steps to recover in, how each step proves itself.

**Two high-frequency gaps** (both really happened in 某工程):

- **"Pending a ruling" scattered in various places** ⇒ "what still has to be settled" becomes "answerable only by reading everything through". **There must be exactly one convergence point.**
- **Goal-level progress written only in a loose-leaf style handover document** ⇒ lost by the next round. **Goal progress is written back only to the one master plan.**

---

## 6. When creating an entity, leave "why + current state" behind

**The rule** (laid down by 某工程's user): when creating a **table／component／page／endpoint／one-off script**,
**at the same time** state two things —

- **Background purpose**: why it exists, what it is to solve, what the original idea was;
- **Current state**: in use / shell / retired / to be assessed (**truthfully**; writing only the intention and not the current state is not allowed).

**The landing point must be nearby** (do not open a separate "entity register" — that will drift at once):
a table goes in the remarks of the registry; components and pages go in the file-head comment; a one-off script goes in a "why it is needed" paragraph at the top.

**Why this clause deserves a section of its own**: the real cost in 某工程 was doubled —
several tables **were built without writing what they were actually for**, and some rounds later: 0 rows in the database, no entry point in the interface, almost nothing in the code referencing them,
**from inside the project it was already impossible to judge what they were meant to implement**, so they could only be deleted. The reason the user gave was "its purpose can no longer be identified,
and when its established function might be implemented later it may not be usable" — **you dare not use it now, and when you want to use it later you cannot pick it back up**.

**Corollary**: **a shell must be marked explicitly**. Registering a capability with **no entry point at all** is worse than not writing it — that is an **empty promise**,
and readers will assume there is a normal path.

## 7. One-page checklist

**Build phase**
- [ ] There is a **ruling document** (the instruction text + three states + a single convergence point).
- [ ] There are three layers of documentation (design / operational / UI), and it states **who prevails on a conflict**.
- [ ] There is an **index searched by situation**, and it states "a new file must be registered".

**Every round of work**
- [ ] Results are reported in **three states** (verified / unverified / known-unsolved).
- [ ] Every change leaves behind **why it was changed this way + the criterion + the measurement output (including the failures and the correction process)**.
- [ ] Rule-type changes are **listed separately as a "semantics change"**, and traced back to a citation.
- [ ] Temporary scripts, instrumentation and temporary data are **cleaned up**.

**Wrapping up / handover**
- [ ] New files are registered in the index; deleted files have their lines struck.
- [ ] The breakpoint ledger has no "missing" items (each has a landing point and recovery steps).
- [ ] Goal-level progress is written in **one** master plan only.
- [ ] The recovery entry point can be executed once through, and every step proves itself.
