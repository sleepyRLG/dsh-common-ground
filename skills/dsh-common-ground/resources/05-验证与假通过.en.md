# 05 · Verification and preventing fake passes: how to know a change is really right

English | [中文](05-验证与假通过.md)

> This chapter is a **cross-cutting plane** outside the three layers — it gathers the parts of 某工程's design layer §9 (verification and delivery discipline)
> and operational layer §4 and §11 (dozens of measured lessons) that are about "**what counts as passed**" into one executable checklist.
>
> This chapter is worth reading on its own, because 某工程's most expensive class of loss is not "not doing it", but **"thinking it was done right"**.

---

## 1. The definition of "passed": three states

**Every time you report a result, there are only three states, and they must not be mixed:**

> **Terminology discipline**: in this series, **"three states" written without a qualifier always means this one (the three evidence states: verified / unverified / known-unsolved)**.
> A "three states" anywhere else must carry a qualifier — such as the "**ruling** three states" in [01 §2](01-协作的基本盘.en.md),
> or the "**three states**" of **layer 4 in the example** in [03 §4.1](03-工程原则.en.md) (allow / explicit refusal / inherit from the layer above) — otherwise the same word has several referents ([06 §1](06-事故台账与断点恢复.en.md) item 14 is exactly that cost).

| State | Meaning | How it must be written |
|---|---|---|
| **Verified** | It ran, and there is a criterion | It must carry **command + output**; writing only "verified" does not count |
| **Unverified** | It did not run, or the environment lacks what it takes | State **why** it is not available (e.g. no desktop session ⇒ the look and feel cannot be verified) |
| **Known-unsolved** | A problem is known, with no solution for now | Register it honestly; it must not be treated as solved |

**Three hard prohibitions**:

- "**Reasonably unverified**" ≠ "passed".
- "**Expected to pass**" must not be written as "done".
- **A skipped item (SKIP) is not a pass** — 某工程 records explicitly that "SKIP is not a pass", and a skip must take an **independent exit code**;
  a looser assertion must not be used to replace the original assertion group.

**Why**: the original logic of `docs/01 §九.2` is — **the value of a self-check equals "whether you would believe it when it fails"**.
Once you allow "unverified" to mix into "passed", the credibility of the whole set of criteria drops to zero.

**Sources**: the red line in `工程根的 README.md`; `docs/01 §九.2`; `docs/00 §11.1`.

## 2. The six forms of fake pass

**"Fake pass" is the core concept of this chapter: the criteria finished running and showed green, but nothing was verified.**

| Form | What it looks like concretely | How to plug it |
|---|---|---|
| **Tautological assertion** | The assertion condition always holds (`|| true`, taking a constant true value for the result, `check(…, true)`) | Ask yourself: **"if the code went back to the shape before the change, would it go red?"** One that cannot go red is a tautological assertion, **equal to not writing it** |
| **Testing what should not be tested** | Using "the statement reported no error" in place of "the behaviour was refused": a certain database does **not fire** the pre-trigger on "0 rows affected" ⇒ the criterion necessarily passes | Assert the **result**, not "no error was reported"; a criterion must be able to construct an input that **must fail** |
| **A skip taken for a pass** | An exception in the cleanup stage is swallowed (printed, not judged a failure); when the environment lacks what it takes, the whole block is SKIPped and still exits 0 | A cleanup block that fails must go through an assertion; a skip takes an independent exit code; **"fewer passing items" ranks as a failure** |
| **A missing scan floor** | "0 violations" is actually because **not a single file was read** | A criterion must carry a scan floor: **"0 hits" must not rest on "nothing was read"** |
| **Defects reported, exit 0 anyway** | The script prints [defect] yet returns success ⇒ in the gate's eyes no different from a pass | **A script that prints defects must count the defects into its exit code**; print a parseable result line |
| **A silent probe** | The probe fails to start, prints nothing, exits 0 — **the one that most resembles a pass** | A probe prints in stages + exit tracing + a timeout fallback; **"not a single assertion ran" does not count as a pass** |

**Sources**: `docs/00 §4.3`, `§11.1`, `§11.2`, `§11.4`, `§11.14`; `docs/01 §九.1`; `证据/S4_裁定落实.md`.

**The reverse also needs guarding against "false red"**: a wrongly written criterion (a clobbered loop variable, a miscount, a bad path join) reports a string of problems that **do not exist**.
A false red itself creates no hidden risk, but it **eats trust** — after one false red, a true red is easily let through as another false red.
For how to handle it see [02 §5](02-动手的纪律.en.md): **when two independent pieces of evidence contradict each other, inspect the criterion first.**

## 3. The seven hard requirements for criteria design

1. **It can fail**: when writing a criterion, ask yourself "if the code went back, would it go red?"; if you cannot answer that, delete it.
   Pair it with a **negative-case control** — build a "before the change" sample, and the criterion must go red.
   > 某工程's own words: **a check that can report "clean" must first be shown to report "dirty".**
   > An instance: the scanner first used the regular expression "a function declaration at column zero", while both duplicate implementations were indented by two spaces ⇒ it reported "0" — **a fake clean bill**.
2. **Bind behaviour, not the carrier**: an assertion binds "where the link points, whether it is disabled, what shape the submitted body has, how large the geometry is",
   **not "the class name or the piece of copy that happened to carry it at the time"** — a carrier is **something a refactor will delete**.
   某工程 hit this 4 times in measurements: once the carrier an assertion was bound to was deleted, a criterion like `indexOf(...) < 0` **went from true to tautologically true**, yet still looked like it was guarding something.
3. **Derive expected values from the facts**: when an expectation can be computed, do not write a string literal.
   某工程 had three same-family false reds within one day, all rooted in **"the expected value was copied by hand"** (pinning a call literal, writing an expected order out of thin air,
   hand-copying a fixture's old value from before a rename). A failure message must **print "expected" and "actual" at the same time**, otherwise, when it goes red, you still cannot tell whose fault it is.
4. **Pin the property, not the literal**: a legitimate reshaping of the implementation causing a false red means the pinning went too far; but **loosen only the literal, never the property**.
   ⚠ Negative-case discipline: quietly changing "each level differs by at least 1px" into "greater than 0" is not fixing the criterion, it is **whitewashing the problem with an assertion that just happens to be satisfiable**.
5. **Grow with the facts**: a criterion must not pin today's snapshot (e.g. "there are N delete buttons in all") — a correct addition will be misjudged as a regression.
   Use a relative measure such as "**did not grow**" in place of an absolute number.
6. **Effectiveness comes before form**: a criterion must be able to **tell right from wrong**, not merely prove that "it ran".
   One criterion that can discriminate beats ten tautological assertions; **"a check was run" is not "it was checked"**.
   ⚠ Three typical shapes of surface verification: **reporting only OK/FAIL with no evidence**, **counting items without looking at content**, **taking "no error was reported" for "it is right"**.
   Their common feature is — **the criterion's conclusion cannot be re-checked by a second person**.
7. **A criterion must be handed to someone else to review**: beside every criterion write clearly **three things** (miss one and it is not "having a criterion") —
   ① **how to re-check me**: a re-run command you can execute directly + the expected output;
   ② **what I do not cover**: the effective boundary;
   ③ **this run's evidence**: how much was scanned, what was compared, the raw output.
   Without these three, a green light only means **the person who wrote the criterion believes themselves**.

**Sources**: `docs/00 §4.3`, `§4.4`, `§11.31`, `§11.32`, `§11.33`, `§A.2`; `docs/02 §三.1b`, `§三.15`.
Items 6 and 7 and the table below are **additions of this round** (source: one real false red — the check script treated variable names case-insensitively and reported 10 differences that did not exist);
**某工程's original text does not have these three**, they are this series' inference.

### A criterion's own three self-proof obligations (channel + method guidance)

| Obligation | Concrete practice (miss one and it is not "having a criterion") |
|---|---|
| **Double-sided self-proof** | A **known-good** sample ⇒ must be green; a **known-bad** sample ⇒ must be red. **One side only = half a criterion** (a false red and a fake pass are exactly the results of verifying one side each) |
| **State the boundary** | Make clear in one sentence **what it does not cover** (e.g. "it judges byte-for-byte identity only, not whether the content is right, and not links or anchors"). **A green light with no boundary written is taken as a guarantee of full coverage** |
| **Leave evidence and a channel** | A run must leave **intermediate evidence** (how many were scanned, the comparison list, the raw output), and give other entities a command they **can re-run themselves**. Records **stay in the project and are not distributed with the reusable artifact** ([07 §4.6](07-文档体系与长期接手.en.md)) |

**Why it stands alone**: a check that **can only report OK** is more dangerous than no check at all — it gives the illusion of "already checked" (exactly the soil in which §2's fake passes grow).
**How a criterion fails must be written beside the criterion.**

**The right to review belongs to other entities**: whoever writes a criterion **must not also be the only one who reviews it** — **hand out** the three things above
(commit them, write them into a document, paste them into a report), so that others can re-check "looking at your criterion", instead of only being able to trust your conclusion.
**"Collaborating reduces hidden risk" rests on a criterion being takeable over, not on trusting each other.**

## 4. Layered verification: what is tested at which layer

| Kind | Where it is tested | Why |
|---|---|---|
| Pure logic, selection semantics | A self-built stub (e.g. Node) | Fast, re-runnable, good for CI |
| **Rendering and interaction** | **A real browser** | A fake DOM written by hand inside Node gives false reports (某工程 got 8 false reports because of it) |
| Data end state | The real database | But **assert only "did not grow"**; absolute row counts are forbidden |
| Authorisation | The real service + **initiated by an account without permission** | A low-privilege identity reading metadata gets a **fake "nothing there"** |

**Two concrete disciplines**:

- **For the database end state, absolute row counts are forbidden**: users really do create data, and absolute row counts will make a batch of scripts report false results together.
  Only ① aiming at the identifiers of the data created by this run ② **no growth from before to after** are allowed.
- **"I cannot run it" ≠ "it need not be run"**: when the environment lacks what it takes, **mark it unverified explicitly**, and have the party that can execute **run the reachable gates on your behalf at once**
  (syntax check, process = disk); do not write the whole batch and then hand it over.

**Sources**: `docs/00 §4.4` (for the database end state, assert only "did not grow"), `§4.5` (rendering-type assertions go in a real browser), `§4.6`, `§11.15`, `§11.8`.

## 5. A probe must prove itself credible

A probe (a diagnostic script, a one-off verification script) is "**the thing used to tell true from false**" — if it is not credible itself, what it gives is a false conclusion.
某工程 has recorded several ways in which a probe itself was not credible: a request rejected for missing a required header, columns recorded into the wrong table, hand-assembled cleanup statements leaving dirty data behind.

**Four requirements**:

1. **Printing in stages + exit tracing + a timeout fallback**; "not a single assertion ran" does not count as a pass.
2. **"Insufficient sample" and "assertion failed" must be separated**: when a precondition does not hold, take "skip" (an independent exit code);
   **only "the element is there and the property does not hold" is judged a failure**.
   > **A false failure is as harmful as a fake pass** — it leads you away from the real problem.
3. **Choose a sample that "can exhibit the property"**: using "the first card" as the sample, when that card happens to have no verifiable content,
   will make 4 assertions fail as permanently false. First prove by query that the sample really has the asserted property, **and print the sample out**.
4. **A probe must not touch real data**: declare destructive paths first; cleanup goes through the one unified implementation in the project, **a probe must not assemble delete statements by hand**.

**Sources**: `docs/00 §11.4`, `§11.5`, `§11.14`, `§11.26`, `§11.3`.

## 6. Discipline from "symptom" to "conclusion"

1. **Stop first, then locate**: do not keep piling changes on in the mindset of "it looks almost done"; first fix the symptom into a **reproducible minimal path**.
2. **Attribute by probe, not by intuition**: **the same symptom ≠ the same mechanism**. Before acting, ask "what other explanation does this symptom have?",
   and make **the smallest probe that distinguishes the two explanations**, aimed at the real service, covering "before the change / after the change".
3. **When the error the user reported cannot be reproduced, do not keep adding guesses**: ask the user directly for **the whole console error (with status code) + the exact operation path**.
4. **Two frequent misjudgements**: ① "the code was changed but the behaviour is wrong" → first check **whether the process is running old code**;
   ② "the assertion went red" → first check **whether the assertion's precondition holds in this context**.
5. **After fixing, look back at the fix itself**: ask item by item "did I change the **cause** or the **symptom**?" If it hits a patch signature (hard-coding an enum to buy space,
   the same property repeated in several places, touching parameters without locating the cause, a correct pattern already in the repository left unused) ⇒ **refactor on the spot; "keep it for later" is not allowed**.

**Sources**: `docs/00 §8.1`, `§8.2`, `§8.2b`; `docs/01 §九.5`.

## 7. A one-page checklist for the natural person

When an AI reports "done / passed", go through these item by item:

- [ ] Is a **command and output** given? (a conclusion alone = unverified)
- [ ] Is the number of passing items **rising** or falling? How many items were skipped, and why?
- [ ] Was the criterion **changed**? If it was, was it "loosening the literal only" or **loosening the property along with it**?
- [ ] Does the "passed" reported this time cover **the path the user will walk**?
      (某工程's high-risk defects grow exactly here: every assertion is right, **and nobody walks the user path they add up to**)
- [ ] Is there an **explicit list of the unverified parts**? (especially the look-and-feel kind that can only be eyeballed)
- [ ] For verification that involves data, was **self-created data** used? Was the temporary data cleaned up?
- [ ] Is there a trace of "run it once and see"? (run the syntax gate right after the change, not three minutes later)
