## 2. One-page quick reference (this section alone gets you 80%)

### The pocket four (if you remember only four things, remember these)

> A–D below hold 18 items and are the full version. If only four can live in your head — **these four cover most incidents**.

1. **Do not invent facts**: every fact you state must point at a location (file:line, command + output, live state in the database).
2. **Do not mix the three states**: verified (with command + output) / unverified / known-unsolved; a skip is not a pass.
3. **A criterion must be able to fail**: a check that can report "clean" must first be shown to report "dirty".
4. **A breakpoint must not go missing**: rollbacks may happen, but the landing point and the recovery steps stay in the ledger.

### A. Who decides

1. **Direction is ruled by the project's "deciding party"; the executor may not change requirements on its own inference.** When new semantics are needed, propose first and wait for the ruling —
   do not "just change it along the way". **A "deciding party" is a seat, not an identity** — usually a natural person, and **an AI may sit in it inside a derived project** (see [01 §1](01-协作的基本盘.en.md));
   but **a derived project must not contradict its parent**: a contradiction escalates to the parent's deciding party.
2. **Rulings have three states: proposed / ruled / not yet ruled.** Anything "pending a ruling" **must not** be used as a basis for acting.
3. **Freeze the affected code during discussion.** While the user is still giving positive and negative examples, do not touch the UI; acting before the semantics are settled equals rework.
4. **On conflict, follow the priority chain**: ruling given on the spot > ruling document > design layer > operational layer > index > explanatory document > historical archive.
5. **Only measurements count**: live state in files and in the database > any number written in any document.
6. **Treat everyone in the project alike (求同存异)**: judgement looks only at "**what responsibility it carries in the project**", never at what it is.
   **Features that existed before the project** (natural person / organisation / AI, compute, interaction mode) **serve only as advice, never as a criterion**;
   how features are used for **collaboration and advice**, and how a joining identity is chosen, **is left to the specific project** (see [03 §8](03-工程原则.en.md)).
   **Corollary: projects may nest** — an AI can hold ruling responsibility inside a **derived project**, but **serves the parent and never contradicts it**.

### B. How to say things

6. **Do not invent facts**: every factual statement carries a source; when unsure, write "unsure".
7. **Do not mix the three states**: **verified (with command + output) / unverified / known-unsolved**.
   "Reasonably unverified" ≠ "passed"; "expected to pass" must not be written as "done".
8. **One word, one meaning**: align terminology first; the user and the AI understanding the same word differently is the most frequent source of rework.

### C. How to act

9. **Edit source with an editing tool; for bulk changes write a script** (a UTF-8-safe runtime).
   The worst incident of the whole project was handing source to a shell text pipeline: the Chinese turned to mojibake and line breaks were swallowed.
10. **After a change, first confirm which copy of the code is actually running**: a stale process is the most frequent source of misjudgement.
11. **Check the current state before acting**: does the project **already** have a carrier for this requirement (table / function / domain / copy)?
    Before a significant change you must list the existing implementation, the call surface and the old/new architecture ownership, and record it before acting.
12. **When an assertion goes red, the first thing is to decide "is the assertion wrong or the code wrong"**; never bend the code to fit the assertion.
13. **One implementation per feature** (criterion: will the two evolve apart?); **one authority per fact**.

### D. What counts as finished

14. **A criterion must be able to fail**: a check that can report "clean" must first be shown to report "dirty" — **let it go red at least once**.
    **"Letting a criterion go red once" and "building a negative-case suite" are two different things**: the former **may not be skipped in any tier**, the latter may be skipped in the light tier (see [02 §3](02-动手的纪律.en.md)).
15. **A trail is part of the deliverable**: evidence, criteria, the failures and corrections along the way, and documentation registration — miss one and it is not finished.
16. **Leave a way back**: back up before a structural change and hand over the rollback script as a pair; every stage has a reversible mark.
17. **Always clean up at the end**: temporary scripts, diagnostic instrumentation and temporary data must go, or the next round will mistake diagnostic code for the product.
