# 02 · Discipline of starting work: tools, order, what counts as passed, how to recover from a deviation

English | [中文](02-动手的纪律.md)

> This chapter corresponds to a certain project's **operational layer** (`docs/00_开发原则_沿用.md`); it governs "**how to do it**", not "what to do" (the latter see
> [03](03-工程原则.en.md)).
>
> Why the operational layer deserves a chapter of its own: every item on this layer comes from **systematic failures caused by tool operations** — encoding round-trips,
> verifying on a stale process, tautological assertions, deleting everything by a fuzzy pattern, changing code after the comments. They are **unrelated to language,
> framework or code quality**: the code can be rewritten, these pits will not disappear.

---

## 1. Tool allowlist: which tool does which job

**This is the section most worth learning by heart first — a certain project's most severe incident happened right here.**

| What is to be done | With what | Why |
|---|---|---|
| Reading a file | **a read tool with line numbers** | convenient for citation and locating |
| Editing an existing file (one place or a few) | **a literal-replacement editing tool** | literal replacement, UTF-8 safe, reports an error on a miss |
| Creating or wholly rewriting a file | **a whole-file write tool** | atomic write |
| Finding a file / finding content | a dedicated search tool | will not run into encoding and line breaks |
| When bulk change is unavoidable (dozens of isomorphic replacements) | **write a Node script** | the runtime is natively UTF-8; convenient for adding counting assertions |

**The incident (really happened)**: a shell text pipeline was used to change one call in a UTF-8 source file; the script host decoded by GBK and wrote back ⇒
the Chinese turned to mojibake, bytes it could not represent became a literal `?` (**irreversible loss**), about 100 line breaks were swallowed, the file had syntax errors;
the automatic reversal afterwards recovered only about 95%, and in the end the whole file was rewritten. **The same pit was fallen into twice in the same round.**

**Three derived rules** (all belong to the class "a tool's implicit assumptions"):

1. **Re-check a script file's encoding marker**: some editing actions strip the BOM ⇒ the script is read as ANSI ⇒ the Chinese is garbled,
   it errors on syntax but the exit code is still 0 ("parsing failed" looks like "it finished").
2. **Never rely on the working directory across calls**: always write paths in full, and do not count on "the current directory" being the one you think it is.
3. **Land output in a file first, then read it**: program output through a pipeline may be swallowed whole, which mistakes "the script died" for "there was no output".

**What you look at**: whether the AI uses "a text pipeline to bulk-change source code", or treats encoding corruption as "a display problem".

**Sources**: `docs/00 §1`, `§1.1`, `§1.2`, `§1.3`; the incident is on file as `事故_api.js被工具误改_20260920.md`.

## 2. Three things before starting work: baseline, facts, way back

### 2.1 First confirm the baseline is green

Run the full self-check once first. **If it is not green you cannot tell "it was already not green" from "I just broke it"** — stacking changes on a wrong baseline makes
after-the-fact attribution impossible.

### 2.2 Read the facts out, do not guess them

- **Existing implementation**: does this requirement **already** have a carrier in the project (table / function / domain / copy)? First `grep` plus read the table structure plus
  check the row and column counts in the database. A certain project's instance: the executor changed the structure on an "assumed" model, while a real carrier table
  **had long existed** in the project, and the two coexisting caused three places of work to point in the wrong direction and
  saves to fail for three consecutive versions (`docs/00 §A.9`).
- **Call surface**: who reads and who writes the existing implementation (server side / relation rules / seed data / frontend / self-check scripts).
- **Data facts**: query the database, do not query the numbers in the documents. **The actual files and the live state in the database > the numbers in any document.**
- **Authorisation facts**: accept only the one way of checking, "the current user's actual authorisation" — a low-privilege identity reading metadata gets a **false "there is none"**
  (a certain project measured: the metadata view returned 53 rows of fake data for a certain account).
- **A comment is not evidence**: judging "whether a certain column/parameter really lands in the database" **must cite a concrete line number**. A certain project had a case where
  "the comment said the opposite", and one wrong comment judged **a whole class of defects** as "not a hole" (`docs/00 §11.18`).

### 2.3 Think about the way back before changing

- Changing structure (DDL/DCL) is an **unreplayable action** ⇒ back up first, and **hand over the rollback script as a pair**.
- Requirements for a one-off script: **idempotent, re-runnable, `--check` first (read-only by default) and `--执行` after**.
- Migration/backfill involving data: the demo-data stage and the real-data stage have **different scales of operation**, and the switch flag = "whether real data has been entered";
  after the switch there must be a backup, it must be rollback-able, and every row must be reviewed (`docs/00 §A.8`).

---

## 3. Decide the tier first: how heavy this job should be

**Why decide the tier first**: the value of discipline lies in **being executed**. Making the same demands of "change one line of documentation" and "change the permission model"
does not make things safer, it makes **the whole set of discipline get skipped** — this series itself writes "**carrying over a discipline nobody executes equals having none**".

| Tier | What counts as this tier | Mandatory | May be skipped |
|---|---|---|---|
| **Light** | Documentation, comments, one-off scripts, pure copy | syntax/consistency check · **one criterion that can fail** (**let it go red once**) · three-state report · cleanup at the end | the negative-case **suite**, the full self-check, probes, backup |
| **Medium** | code changes for a single feature, **not touching** structure / semantics / permissions / data | **the four gates** · the criterion can fail (with a negative case) · sync the affected old criteria | probes, backup scripts, breakpoint ledger |
| **Heavy** | table structure · field semantics · permissions · data writes · interface contract · shared components | **everything**: the four gates plus a negative case plus a probe or real-environment verification plus backup and rollback scripts plus a breakpoint ledger plus documentation registration | none |

**Four tiering disciplines**:

1. **Judge by "the worst consequence", not by "how many lines were changed"**: changing a 1-line permission judgement is the **heavy tier**.
2. **When unsure, lean to the heavier tier** (a certain project's stance: "rather write more").
3. **Three things no tier may skip**: **a three-state report · cleanup at the end · one criterion that can fail**.
   A light tier's criterion is often just a check like "verbatim identical" — it likewise must first be able to report "dirty".
   > ⚠ **Do not mix two things into one**: "**letting this criterion go red once**" is **the minimum obligation of any tier** (a criterion that cannot go red does not count as a criterion);
   > "**building a negative-case suite**" is **systematic negative-case control**, and the light tier may skip it. What the light tier skips is the **suite**, not that one red.
4. **On discovering that structure / permissions / data are involved, escalate the tier at once**, "let us start on the medium tier and see" is not allowed. Escalating is allowed at any time,
   **de-escalating needs the user's nod**.

> ⚠ **The source of this item (three states, do not take it as a certain project's own text)**: a certain project **had no** written tiering — its whole generation was executed as the heavy
> tier (the four gates always open). This tiering is **this series' inference**, based on its sentence "carrying over a discipline nobody executes equals having none" and its stance of
> "rather write more", and **it is not verified in the field**. If you really want to use it, it is advisable to try one tier on a small project first and then decide.

**Sources**: `docs/00 §0`, `§4.1`, `§A.8`; `docs/01 §九`;
`证据\S3.5_界面契约重建.md` (**where the very sentence** "carrying over a discipline nobody executes equals having none" **is**, line 160).

## 4. The four gates (pass them in order; skipping a step does not count)

| Gate | Action | Passing criterion |
|---|---|---|
| 1 | syntax-check every file you changed | no errors |
| 2 | start/restart the service, confirm **process = disk** | the health endpoint returns a build fingerprint **computed from disk right now**, matching the local one |
| 3 | run the **affected** self-check scripts | all related items pass |
| 4 | run the full self-check | every script exits with code 0 |

**Why gate 2 cannot be skipped**: the cause of a certain project's two big incidents was both times "a stale process was still running the old code", and both times it opened with
"the code was changed but the behaviour is wrong"; on one occasion the user reported "the table is not registered", and the real cause was that what ran on the service was **a process
started by the previous session**. ⇒ **the authentication fingerprint must be computed from disk right now**, you cannot rely on "I restarted it just now".

**Why a gate must be wired the moment it is built**: a certain project has a record that says "the gate was built but nobody calls it". **Building it without wiring it equals having none**
(`docs/00 §11.2`).

## 5. What to do when an assertion goes red (the order may not be reversed)

**The first thing is always to decide "is the assertion wrong or the code wrong", not to change the code to make it go green.**

Both classes really happened:

- **The assertion is wrong**: the use case's premises contradict each other (two assertions cannot both be true) ⇒ the handling is **to build the missing premise**, not to loosen the criterion;
  the statistical definition had not excluded historical carry-over rows ⇒ tighten the criterion to the real semantics.
- **The code is wrong**: the visibility SQL is missing a branch (a set-type judgement has no corresponding branch on the path that reads by table) ⇒ change the code and **add an assertion to lock it down**.

**Four supporting disciplines**:

1. **A failure must not be explained away**, and "as expected" must not be allowed to cover a real defect; on finding an assertion written wrong, **change it on the spot into "an assertion that can fail" and re-run**.
2. **Attribution relies on a probe, not on intuition**. A certain project's instance: the same symptom was explained as "the login snapshot expired", while the real mechanism was "the set
   judgement is missing a branch"; in the same round three further "suspected defects" were **all falsified by the probe** — acting without falsifying them first would have changed three places for
   nothing. Before acting, ask one question: **"what other explanation does this symptom have?"** When two explanations point to different fixes, first make **the smallest probe that distinguishes the two**.
3. **Loosen only the letter, never the nature**: when an implementation legally changes shape and causes a false red, changing the criterion must keep the "nature" still pinned down;
   a certain project judged "secretly changing `≥1px` to `>0` to cover up the exception" outright as **"whitewashing the problem with an assertion that happens to be satisfiable"**.
4. **A false red is handled in the same order too: check the criterion itself first.** A criterion will report problems **that do not exist**
   (a clobbered loop variable, a miscount, a bad path join). The practice: run the criterion once each on two samples, "**known good plus known bad**";
   **when a criterion has a bug of its own, that whole output of its is void**, fix it, re-run, and only then draw a conclusion — **do not rush to change the thing under test**.
   > A real case: a comparison script contained `$i = $I | Where-Object ...`, and PowerShell **variable names are case-insensitive**,
   > so `$i` and `$I` are the same variable — the first round of the loop overwrote the file array with a single object, and so it reported 10 differences **that did not exist**.
   > It **contradicted itself** with "11 lines of hashes are fully identical" in the same output; and it is precisely this contradiction that shows **what should be suspected is the criterion, not the files**.

---

## 6. Data-touching discipline

1. **Name the operation before running anything that writes data**: which tool, which block of data it changes, whether it can be rolled back. When a user declares "do not touch a certain
   data during re-verification", **you must not** write to it (including "rollback-able" writes).
2. **Experiment only with self-made data**: a temporary-prefix project / a temporary database. Real projects and demo projects **must not** be used as an experimental field
   (a demo project is a **deliverable**, not test data; when a script detects manual changes it must **refuse to rebuild**, and needs an explicit `--force`).
3. **Cleanup is directed only at an exact target**: bulk deletion by conditions such as "fuzzy prefix match", "the field is empty" or "time range" is **forbidden**.
   A certain project's incident: a temporary cleanup script deleted everything by prefix and deleted a temporary project **that a parallel job was running**, so the interference had already
   happened and could not be rolled back (`docs/00 §11.13`).
4. **The timestamp convention must be uniform**: writing to the database uses the local convention, display uses local formatting, and **conversions that treat local time as UTC are forbidden**.
   A certain project's incident: a diagnostic probe used a UTC conversion to write a date column ⇒ 14 real tasks each had their date moved back a day, and it was corrected only by
   backfilling field by field from an append-only change log (the side effect of rev advancing 2–3 times is **irreversible**).
5. **Hard-delete temporary data when it is no longer needed**, do not leave it in the database for someone to find.

---

## 7. Must-dos at the end (otherwise the next round will mistake diagnostic code for the product)

- Delete temporary scripts and diagnostic instrumentation; confirm the instrumentation keywords have **0 hits** in the source.
- Confirm the script files' encoding markers are still there.
- Confirm the temporary data has been cleaned up and the database end state has "not grown".
- Enter the breakpoint into the ledger (see [01 §6](01-协作的基本盘.en.md)) — **a rollback may happen, a breakpoint must not go missing**.

---

## 8. The six mistakes AI is most prone to on the operational layer

| Failure mode | Recognition signal | Response |
|---|---|---|
| **Treating "I cannot run it" as "it may be left unrun"** | the delivered code carries defects "one run would have found" (e.g. the interface returns 500 every time) | code that was not run is **explicitly marked "unverified"**; the party with the means to execute **immediately runs the syntax gate in its stead**, without waiting for the whole batch to be closed out |
| **Attributing by intuition** | the symptom already has an explanation you "casually" reached for | write a probe first and falsify; paths/table names/class names **are copied from the tool's output**, not retyped from memory |
| **Manufacturing a "pass" yourself** | the "green" comes from zero output, skipped items, a tautological assertion, or "reported a defect yet still exited 0" | **for the six forms of fake pass and how to plug them see only [05 §2](05-验证与假通过.en.md)**, not repeated here |
| **Tool self-injury and cleanup over-reach** | the encoding turns to mojibake, line endings change, someone else's data is deleted | make the tools an allowlist; delete only by an exact target |
| **Delivering a process artifact as the product** | a temporary short-circuit marker, instrumentation, a half-finished piece left on disk | the four end-of-work checks (see §7) |
| **Fast but not closing out** | "it looks like it is nearly done", so you keep stacking changes | **stop first, then locate**: fix the symptom into one reproducible minimal path |
