# 04 · UI contract: turning "I want it to look like this" into executable rules

English | [中文](04-界面契约.md)

> This chapter corresponds to a certain project's **UI layer** (this generation `docs/02_界面契约_重建.md`, taking over the first generation `交互策略.md`).
> It governs three things: **display (what it looks like) · interaction (how it responds) · language (how it is worded)**.

---

## 1. Why the interface needs an authority of its own

**Appearance and wording can be derived neither from the data model nor backwards from the implementation code.**
The data model holds no answers to "how many font-size tiers", "should the button have a border", "should an error carry a person reference".

**The value of a "UI contract"**: turning **one user's preferences** into **clauses that are citable, criteriable and re-verifiable**.
Without it, the AI does two things every round — "the old version had it and now it does not, put it back", or "read on and expand along the previous sentence",
so the same thing gets overturned again and again. A certain project recorded one real drift of direction: the user said "the old proposal is closer to the target effect",
and the executor expanded it into "appearance and in-page layout also follow the old case", restoring item by item anything that "the old version had and the current state does not" as a defect.

**Three meta-rules**:

1. **The contract precedes the code**: a new UI element **is first registered as one line in the contract (stating its landing point and its basis), and only then implemented**.
2. **Three in one, from one source**: **contract → machine-checkable criteria → visual re-check list**. Miss one and it drifts again:
   the clauses sit in the document, the conventions sit in the code, and nobody notices when the two disagree.
3. **What it constrains is appearance and rules, not where the skeleton comes from**: the DOM skeleton and the way components are organised are implementation freedom.

**Citations**: `交互策略.md §0`; `docs/02 §一`, `§七`; `docs/12 §四.3`.

---

## 2. How the contract is maintained: pointers + a difference list

**Rule**: the clause text **is never transcribed a second time**; when carrying over an old contract, use "**a carry-over list (each item marked same/different)
plus a difference list (how the old case put it → how this generation rules it → why) + the elements only this generation has + an unchecked list**".

**Why a pointer alone is not enough**: the old clauses were written **under a different set of premises** (a certain project's example: the old contract laid down "the stylesheet is append-only and old
rules must not be changed", on the premise "take the old panel's stylesheet as the baseline" — and in the new project that baseline **does not exist at all**).
So "is the premise still there" must be judged item by item, and **a clause whose premise is gone must be explicitly voided**.

**Supporting discipline**:

- **Unchecked ≠ carried over**. An unchecked clause **does not count as the current convention**; when citing it, "unchecked" must be noted in the same sentence; once an item is checked, move it out,
  leaving one line for "when it was checked and what was found".
- **Carrying over a discipline nobody executes equals having none.** The old contract's "zero violations" rested on a check script that was never
  brought into the new project ⇒ the convention might as well not exist. **Whatever can be expressed as an assertion must have an assertion.**

**Citations**: `docs/02 §一`, `§二`, `§三.7`, `§五`, `§六`, `§七.1`–`§七.4`.

---

## 3. Display principles

| # | Rule | Why / how to do it |
|---|---|---|
| 1 | **An element derives from the function it serves** | Whether an element exists, its form and its size are decided by what function it serves; **it is not that a layout comes first and functions are stuffed into it**. Facing an uncovered new situation, first ask "what function does it serve? how much space, how much information, what operations does it need?" |
| 2 | **Never compress the space a function needs in order to fit an existing layout** | An editing area handling large blocks of text must be given enough height |
| 3 | **The same information appears only once** | Information already expressed by a higher level (group header / column header / context) is not repeated in each subordinate row; when a row really must carry it, treat it as **an exception with the reason stated** |
| 4 | **Separate information from operation** | The operation area holds only action buttons; status/hint text ("end", "read-only", "inherited") is information and goes in an information position |
| 5 | **The clickable area must be narrow and predictable** | The hot zone is limited to the explicit marker + the name, with hover feedback; statistics and counts are not inside the mis-tap range; **a count must be semantically self-evident** (write "sub-level entries N", not a bare abbreviation of the "(sub N)" kind) |
| 6 | **Clipping a whole block takes priority over ellipsis** | Units that are semantically indivisible (name + trailing label, status pill, count, button text) never wrap and are never clipped; when space runs out, **wrap the whole block** or widen the container; ellipsis is allowed only for a clearly special need, and **the reason is stated in the code** |
| 7 | **Status never relies on colour alone** | Use a symbol or a line style + text; guarantee it stays distinguishable in greyscale printing and under colour-vision differences |
| 8 | **One screen is a budget** | The levels above the table header must be capped ("top bars ≤ 2", "above the header ≤ 3 levels"); column widths **must not be inferred from the currently visible content**, or folding/unfolding makes the column names jump left and right — the header and the body **share one and the same column-width definition** |
| 9 | **Proximity is monotonic** | The spacing gradient increases monotonically (e.g. 4 < 8 < 14), tight within a group and loose between groups, with no new tiers invented |

**Citations**: `交互策略.md §1`, `§二`, `§2.5`, `§5.1`; `docs/22 §6.3`.

## 4. Interaction principles

1. **The row itself is the control**: the whole row is clickable for the most common action (e.g. checking a box toggles the state); structural maintenance goes into a dialog.
2. **One action keeps one entry point only, and viewing and changing do not share a screen**: any mutating action (create / edit / delete) is collected into **a single entry point**,
   and must not share a screen with read-only content; while the entry point is closed the list is simply read-only.
   **Why**: two write paths make the same piece of data go through its pre-validation twice, and the user cannot tell "can this be changed here".
3. **Do not pass off another element as a control**: do not render a read-only display as a disabled control ("looks clickable, does nothing when clicked");
   express the read-only state with a **symbol**; where there is no permission, write "read-only", not the same shape as "no value".
4. **A selector has only two shells, decided by "bounded / unbounded"**: bounded single choice = a native control; unbounded multiple choice = a summary row (selected tags + "N selected" +
   an explicit expand/collapse) + an expand area (search + candidates scrolling within a height cap). The two shells **share one implementation of the candidates and the selected state**;
   collapsing, searching and checking make **zero requests**, and a request is sent only on save.
   **Why**: one self-drawn control forced to carry both needs inevitably gets neither right (after collapsing you cannot see who was selected, there is no search, and there is no explicit expand entry point).
5. **Feedback is prompt and precise**: validate at the moment of the action and **name the object and the reason** ("this stage still has 3 tasks, move them away or re-attach them first");
   when blocked, **the row does not disappear** and shows inline red text; a removable item is marked "to be deleted" (the row stays and can be undone), and is really deleted only after saving;
   a row just touched must be recognisable (an outline / an immediately updated sequence number).
6. **Failure must be distinguishable by layer**: always display **an error code + a status code**, never only a Chinese description;
   "insufficient permission" must let you tell which layer it was; an optimistic-lock conflict must prompt a refresh;
   **a record you cannot see is refused for read and write alike** (do not leak its existence).
7. **A missing capability generates no control**: never display a button that refuses when clicked; **when the capability is false, do not even generate the button** (not disabled).
   **Why**: both "visible but unclickable" and "invisible yet writable" come from the UI and the server side **each computing its own set of permissions**.
8. **Status does not lie**: the UI must not promise an operation the server side will not honour; the empty state and the count come from the same source; when rendering fails, write
   "rendering anomaly" truthfully, and **never write "no data for now"**.

**Citations**: `docs/02 §三.4`, `§三.5`, `§三.6`, `§三.19`, `§三.20`, `§四.20`, `§五之二`;
`docs/22 §一`, `§二`; `交互策略.md §5.2`, `§5.5`.

## 5. Language principles

**Guiding idea**: **clear semantics, amiable and neutral** — state "what it is · why · the next step" clearly, while **introducing no person for the speaker or the listener,
passing no judgement and showing no emotion**.

1. **One sentence = object + fact + next step**; terminology matches the data model word for word; numbers carry units and bounds;
   do not use "this operation / this feature / related / the above" without an antecedent.
2. **No implementation words**: UI copy must not contain the data model's implementation concepts (table / column / row / edge / node id),
   and always says instead what the user can see ("subordinate", "child item").
3. **No person**: do not write "you / I / we"; use a role name or a subject-less statement instead.
4. **Do not judge people, do not show emotion, no pleasantries**: do not write "error / illegal / invalid input", write only the fact and the consequence;
   no exclamation marks; do not write "sorry / thanks / please wait".
5. **Consistent and restrained**: synonyms always reuse **the single-point word list**; buttons use the **verb–object form** (create · edit · delete · restore · submit · withdraw),
   states use noun phrases; one page must not contain two synonymous wordings.
6. **One word, one meaning**: maintain a "baseline table of appellations and terminology" (the only allowed wording / which wordings not to use);
   e.g. the logged-in person themself → "current account", the task owner → "execute", the document author → "create".
7. **Exceptions must be allowlisted**: the data itself (names and notes entered by the user) is not constrained; historical archives are not rewritten;
   an exception that is genuinely necessary goes through the process (proposal → approval → allowlist registration → audit trail), so that "zero violations" becomes **mechanically provable**.

**Citations**: `交互策略.md §6.1`–`§6.4`; `docs/02 §五`.

---

## 6. Four kinds of explanation may not be hidden

**Empty-state guidance · blocking and risk · data semantics · state and permissions** — folding these four away equals lying
(the user does not know "why it is empty" or "why it cannot be clicked"). **An explanation is not decoration; it is the minimum degree of honesty.**

Implementation: one sentence always visible (advised ≤ 28 characters, cap 40 characters); the rest go into an information popover (cap 120 characters); the always-visible total has a budget;
the copy is **single-pointed** in one word-list file, and an audit function asserts the caps directly.
When delivering an interface you must **answer item by item "where are these four kinds of explanation"**, otherwise it counts as unfinished.

**Citations**: `交互策略.md §5.2`, `§5.4`; `docs/02 §二`, `§三.10`.

## 7. Write the machine-checkable part as criteria

| Criterion | Key points |
|---|---|
| Token and value allowlist | The token set, the font-size tier allowlist, **strictly decreasing** (even a 0.5px exception is honestly registered as one assertion — **do not secretly turn "≥1px" into ">0" to whitewash the exception**) |
| Document and code agree | The token set in the contract file must be **exactly the same** as in the code; no dangling references |
| Zero hard-banned words | Any hit of a hard-banned word is a defect; caution words only warn; exceptions are allowlisted |
| Class-name closure | Every class defined in the styles must be used by someone; every class used must have a rule or be in the allowlist |
| Inline long-sentence cap | The number and the positions of long sentences are bounded by a budget |
| Clauses in place | Every clause in the contract can be traced to a landing point in the code |

**Two supporting disciplines** (otherwise criteria become a placebo):

- **Scan floor**: too few files/literals scanned means failure, **guarding against "nothing was scanned yet it counts as passed"**.
- **Negative-case control**: break the correct thing and the criterion must go red.

**Citations**: `docs/02 §三.8`, `§三.1b`, `§三.14`, `§三.15`, `§五`.

## 8. Discussion flow: the deciding party commands, the executor must not infer

> **"Deciding party" is a seat, not an identity** (see [01 §1](01-协作的基本盘.en.md)): usually a natural person sits in it,
> but **an AI may sit in it inside a derived project** — this section's four items **follow the seat**, regardless of entity category.

1. **The proposal system**: the executor first produces a **proposal** (options, consequences, preference, **no code**) → the **deciding party** ticks or rewrites →
   the ruling goes into the ruling document → then the contract is written → then the code is changed.
2. **Segment-by-segment registration**: every segment of the **deciding party's** instructions is registered sentence by sentence into a ledger (key wording / my understanding / the issue it corresponds to / landing point and status),
   and it is marked "whether this is now the stage of exchanging views or a ruling".
3. **Freeze the related code while the discussion is unsettled**: a certain project's exact words were "**I will not touch the UI code until you have finished with the positive/negative examples and the ruling**"
   (the side that says this carries the **ruling responsibility**, the other side is the **executor**).
4. **The words "the old version had it" are forbidden in a change rationale**: that treats an old implementation as a requirement.
5. **Re-verification tells two kinds apart**:
   - what **can be machine-checked** (names, values, wording, geometry) → written as assertions;
   - what **can only be eyeballed** (colour harmony, appropriate level of detail, appearance not regressing) → a **re-check list** is produced for a person,
     explicitly marking "what this version still cannot verify — do not report it as a defect".
   With no desktop session, anything about appearance is **always recorded as "unverified"**, and must not be written as "re-verified".

**Citations**: `docs/12 §一`, `§三`, `§四`, `§七`, `§八`, `§九`; `docs/13 §九.2`.

## 9. The seven mistakes AI makes most easily at the UI layer

1. **Expanding one word of approval from the user into "do the whole area as before"** ⇒ the words "the old version had it" are forbidden in a change rationale.
2. **Using old clauses whose premise has changed as a basis** ⇒ the carry-over list marks each item "same/different", and clauses whose premise is gone are explicitly voided.
3. **One self-drawn control forced to carry two needs**, so patches keep piling up ⇒ write the spec and the criteria first, then write the code.
4. **Tying an assertion to a carrier that will disappear** (the class name of the day, that piece of copy) ⇒ after a refactor the assertion turns from "true" into "always true" while still looking like it guards
   something (a certain project measured this 4 times). **Assertions are always tied to behaviour** (links, the disabled state, the shape of the submitted body, geometry), not to carriers.
5. **Criteria too narrow, causing a fake pass**: only a few keywords are checked and a dozen violations all slip through ⇒ allowlist-style criteria + a scan floor + a probe negative case.
6. **The UI and the server side each computing its own set of permissions** ⇒ permission judgement happens only on the server side, and the UI merely presents the conclusion.
7. **Using pseudo-controls for information, and lying in the empty state** ⇒ read-only uses a symbol; the empty state and the count come from the same source, and a rendering anomaly is reported truthfully.

**Citations**: `docs/12 §一`; `docs/02 §三.7`, `§三.15`, `§三.6`; `交互策略.md §7`.
